# R3 bounded reference-vector and refusal review

Pinned proposal `05c0e61961be5befa0485b589e45447bbaa5f78a`. `r3-reference-results.json` records independent execution of its unchanged Appendix A Python example and additional calls to its f64 encoder. Base/fresh digests match the published vectors, illustrative reconstruction equals fresh, signed zero encodes equally, and NaN/positive infinity/negative infinity each refuse. This is not a real producer, Swift consumer, resource-binding or visual test. No delta parser was added.

R3 corrects stale installation, measures reconstructed target rather than wire delta size, distinguishes digest consistency from fresh-full completeness and names the explicit CFF binding path. It appropriately keeps the existing Rust binder on original full bytes rather than adding an unchecked model entry point.

Two residency blockers remain. Section 6.2 permits an over-16-MiB target to be validated and painted but not retained as a base, while claiming the candidate is capped at 16 MiB. Base eligibility does not remove the painted/decoded target from residency. Either refuse before exceeding the cap, or explicitly specify and charge a separate bounded full-only path; do not retain the present peak claim. The cited native coalescer also holds an in-flight preparation, queued input and previous frame simultaneously. Replacing a queued item is not cancellation of the active callback or reclamation of its models/fonts/rasters. Account for these allocations and backpressure before asserting two slots plus one line is the complete bound.

`refusal-scenarios.json` gives concrete machine-readable review cases for a 4 KiB delta reconstructing a 16 MiB + 1 byte target, stale B between painted A and next C, and active-plus-queued residency. They map to existing full-event/currentness guards but are explicitly **not delta wire fixtures or passing implementation tests**. The stale-B rule is corrected in r3; its eventual implementation still needs these checks at publication and use. Existing full-resync refusal stays mandatory. No activation approval is given.
