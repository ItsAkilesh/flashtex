# Independent Aarush compiler/PDF compatibility review

Pinned peer `0236aa0a74413fd997c15b31b885bfde941c4325`, branch `agent/aarush-macbook/incremental-reuse`, compared only with merge base `29221d8b15d412f4feb877879d5bfc02f6086a98`. Changes are ten compiler paths (1,554 insertions, two deletions), including older PDF addition `96f1d968`, cache and later tests. No merge, build or native call was made. The owner's 125-test report is not independently rerun evidence.

**Do not adopt the branch wholesale.** It is based on the older single-document Span and placeholder-ratio layout, not the current compiler's multi-document span/incremental math/export interfaces. All changed paths belong to the compiler owner; the proposed new PDF path also overlaps the established original PDF subsystem's purpose. Tests may be selectively reviewed for useful coverage after current-owner porting, but a passing old-tree suite is not current integration acceptance.

Confirmed source-level blockers:

1. `protocol.rs` cache-hit path unconditionally emits `status: ok` and an empty diagnostics array. `CachedResult` stores neither status nor diagnostics, while all compile results are inserted. Two identical unsupported/malformed inputs therefore turn the second result into apparent success, violating recovered-output/error visibility and clean/incremental equivalence. The cache needs complete output semantics, not only pages and a path.
2. `pdf.rs` emits every word through Helvetica, with unsupported Unicode replaced by `?`. This loses already supported Greek/math and the new membership/quantifier symbols instead of using the compiler's explicit export mappings or the renderer's original-GID resources. The encoder describes CP1252 but its font dictionary does not explicitly declare that encoding. Source comments acknowledge limitations, but runtime consumers receive a non-null PDF path without a corresponding substitution diagnostic.
3. Geometry and sizing are weakened: all f64 page/position/font values cast to f32; font size changes within0.01 reuse the previous size. No exact geometry or font-identity compatibility follows from PDF-header/raw-Hello tests. The output contains no retained source/cluster/font-resource provenance. It cannot stand in for the existing exact mixed/CFF exporter.
4. A cached PDF pathname is mutable external state. Later identical source returns the old path without checking file existence or bytes. Deterministic `/tmp/flashtex/<sanitized-project>/rev<revision>.pdf` names collide across processes/sessions and sanitized/truncated project IDs; `File::create` overwrites directly rather than publishing an immutable atomic result. A different compile can overwrite a cached path, so the returned pages and PDF may no longer correspond. No consumer may infer currentness or immutable output identity from it.
5. `pdf-writer = "0.15"` introduces another container writer instead of consuming the already owned original PDF API. This needs an explicit architecture/ownership decision; it is not evidence of the requested from-scratch exporter or an authorized replacement. The dependency change must not be swept into integration with unrelated lexer/Span tests.

The cache verifies exact text after its hash, which avoids treating a hash collision as equality; its LRU promotion is useful in isolation. Those points do not repair lost diagnostics, incomplete identity/configuration keys or mutable PDF outputs. The branch's Span tests also use its old two-field representation, so porting must preserve current document identity.

Recommended next owner action: retain the branch as review material, separate useful test-only increments, and reject/repair the semantic cache-hit bug before any current-tree integration. Existing compiler and PDF owners should select compatible work; do not start a duplicate exporter or claim PDF/reference/native parity. No issue closure or remote adoption was performed by this reviewer.
