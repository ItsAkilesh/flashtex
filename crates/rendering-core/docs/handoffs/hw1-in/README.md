# HW1 narrow math-owner handoff: membership relation

Prioritize `\in` as one bounded compiler/math integration task after the starred-heading work. The immutable HW1 gap report records 12 unsupported membership commands; direct source inspection finds 12 occurrences, pinned with UTF-8 byte ranges in `source-pins.json`. The fixture uses them both in inline `$a,b\in\Z_{>0}$` and quantified display formulas. This recommendation removes one frequent literal-command failure without requiring a new math alphabet AST or another parser. It does not claim the rest of those formulas will render correctly: `\mathbb`, quantifiers and other constructs remain separate.

## Existing chain and smallest change boundary

1. Compiler `crates/compiler/src/math.rs` at reviewed main `7d8f323a…` and producer dependency `9aaec57a` has `MathAtom { nucleus, span, superscript, subscript }`, with `Nucleus::Symbol(String)`. `command_atom` asks `COMMAND_GLYPHS`; `in` is absent. The current error records the command span, then emits literal `\\in` as a Symbol. Add recognition through this existing table rather than rewriting math parsing. Retain the original command-token span and script attachments; rendered text becomes the single U+2208 scalar, not the raw TeX spelling.
2. `crates/render-pipeline/src/typeset.rs::convert_math` already converts a single scalar to `ml::Atom::symbol`. Its present multi-character literal-command path emits an upright ordinary group, explaining the current semantic failure. `crates/math-layout/src/mathlist.rs::default_class` already classifies U+2208 as **Rel**, preserving the existing relation-spacing rules instead of inventing spacing in the renderer.
3. `crates/math-layout/src/cm.rs::symbol_slot` already maps U+2208 to **Symbol family / TFM slot 0x32**. `TexMathMetrics` uses that font/code's exact metric path, while `mathtex.rs::otf_gid` resolves the Unicode character through the actual Latin Modern Math face cmap. **TFM slot 0x32 is not an original OpenType GID.** Preserve family, metric size, actual face identity and returned original GID. Missing glyph/resource remains a typed diagnostic; no `.notdef`, font substitution or hardcoded GID.
4. The direct compiler export path is separate: `export.rs::SYMBOL_ENCODING` currently lacks U+2208, and `every_math_symbol_has_a_decided_export_outcome` iterates `COMMAND_GLYPHS`. The owner must provide a verified Symbol encoding mapping there as part of recognition or explicitly revise that route's accepted support policy. Do not cast Unicode or the CM slot into a PDF code. This handoff supplies no guessed byte mapping.
5. Pipeline `math_items` converts positioned math glyphs into existing display runs using the actual face/GID and source provenance. It presently assigns **the whole math expression span** to each glyph cluster, because `convert_math` drops individual atom spans. Preserve this truthful coarse provenance for the bounded recognition change. Command-level clickable spans require an explicit separate source-carrying adapter change; do not infer offsets from glyph order, Unicode byte length or TFM slot. An inserted U+2208 has three UTF-8 bytes while the original `\in` token has its own original range.
