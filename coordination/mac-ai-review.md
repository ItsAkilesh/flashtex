Ready behavior (all in ProposalPreview.swift; the review sheet's existing call surface `ProposalPreview(executable:)`, `update(from:latex:)`, `retry()`, `close()`, `ProposalPreviewView`, `ProposalApproveWarning` is unchanged; `ProposalPreviewView` now renders `ProposalExplanationView` at its bottom, so ContentView needs no change to show it):
- `explain()` (explicit "Explain" button; never automatic) runs the pinned `flashtex-assistant-context` as a one-request child process (`OneShotProcess`: stdin then EOF, stdout bounded 128 KiB, stderr bounded, timeout 10 s, SIGTERM then SIGKILL, completion once on main) with `operation:"prepare"` bound to the shadow compile: `binding.request_id` = the shadow worker request id (`preview-N`), `compile_revision` = its revision, `sources` = every shadow document as an edit-ledger Document (project `<project>-preview`, revision = editor revision, SHA-256 of text), `compiler_result` = the runtime-v1 `compile_result` envelope re-encoded with explicit `source:null`, `selected_diagnostics` = new-vs-baseline, then inside the insertion, then nearby (≤16), `user_instruction` names the proposal bytes. Two prepare calls: a probe without destinations, then the bound context with explicit `destinations` = the proposal body clipped to the snippet that overlaps it most (or `[]` = explanation only). The Swift side refuses a prepared payload without an explicit `allowed_edits`, or whose revision/project differ from the binding.
- Provider: disabled by default. Only when the user sets `FLASHTEX_ASSISTANT_PROVIDER=<executable>` (plus optional `FLASHTEX_ASSISTANT_TIMEOUT_S`, capped 120) the prepared `PromptPayload` bytes go to that local command's stdin (reply ≤ 64 KiB, timeout 60 s). FlashTeX itself opens no network connection; a provider command may, only because the user configured it. Without a provider the state is `.prepared(context)` with the text "No provider is enabled — nothing was sent" and the context id / diagnostic count / bytes / edit boundary shown.
- The provider reply goes back through the helper: `validate` when it proposes no edits (explanation only), `review` (with `explanation_request_id`) when it does → `proposal_review` with `review_id` and `requires_user_approval:true`. Displayed as "Assistant — model output — never applied automatically": explanation text, each proposed edit as −removed/+replacement with its proposal byte offset and a Copy button. Refused (state `.failed`): `applied:true` from the helper, a context id mismatch, edits outside `allowed_edits`, a `proposal_review` without review id/approval flag.
- Explicit "Approve edit to proposal" → `approveReviewedEdit()` → helper `approve` with `user_approved:true`, `approved_review_id` = the exact review id, `current_sources` = a fresh snapshot of the shadow documents → `approved_group` (`applied:false`). The Swift side checks review/request/project/path identity, `command_id == "assistant-<review_id>"`, `expected_revision`/`expected_sha256` against the shadow text, each edit's `removed_text` against the shadow text inside the proposal body, and that the group equals the reviewed edits; then applies the edits to the proposal body only → `amendedProposalLatex` (state `.approved`, "Copy amended proposal"). The editor buffer is never written by ProposalPreview; inserting into the document stays the sheet's existing "Approve and insert" through ShellModel/edit-ledger.
- Cancellation (follow-up 1): `update()` with any change to documents, anchor, editor revision or proposal text, and `close()`, terminate the in-flight helper/provider process and set `.cancelled(reason)`; an identical update keeps a finished explanation. Every completion is routed through `handleExplanationReply(id:stage:result:)`; a reply whose request id or stage is not current (cancelled, superseded, `.done`, forged) increments `staleExplanationReplies` and changes nothing. A helper answering another compile revision is rejected.
- Recovery (follow-up 2): helper crash (exit 3/5), hang (timeout), garbage or oversized output, provider crash/hang/garbage, at probe/prepare/provider/validate/review/approve stages → `.failed(reason)` while the shadow preview stays `.ready`, the shadow text is intact, `canExplain` is true again, the worker stays alive, `model.documents/result/editorRevision/pendingEdit` are unchanged, and `rejectProposal`/`approveProposal` still work with the reviewer's own text.
